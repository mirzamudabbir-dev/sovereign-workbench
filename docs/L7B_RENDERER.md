# L7b — DELIVERABLE RENDERER

## MISSION LOCK

**Build:** deterministic rendering of a validated `RenderPlan` into real Word, PowerPoint and
Excel files, with every asserted value resolved against a real `EvidenceSpan` before a single
byte is written.

**You are NOT building:** the LLM prompt that produces the plan (L4 owns that), the UI, or
retrieval. You receive a `RenderPlan`, you emit a file path — or you refuse.

**Serves:** R9 (real deliverables: Word/PPT/Excel, calculations with steps shown), R13.

**Files You Own:**
```
core/render.py
templates/approval_note_v1.docx
templates/board_deck_v1.pptx
templates/calc_sheet_v1.xlsx        (generated by openpyxl, no template file needed)
tests/test_render.py
```

## The rule this entire layer exists to enforce

> **The LLM never writes binary office files.** It emits a schema-constrained `RenderPlan`.
> This layer resolves every `evidence_ref` against the KB, and only then renders from a
> template owned by the organisation.

Consequence, and this is the sentence to say on stage: *a hallucinated pressure rating is not a
fluent sentence someone signs — it is a validation error that fails closed before a file exists.*

If you weaken this — by letting a field through without evidence, by rendering "best effort" on
a resolution failure, by having the model emit XML — the project loses its main claim. Don't.

class EvidenceResolutionError(WorkbenchError):

    is used in a numeric field without explicit human confirmation."""


def validate_plan(plan: RenderPlan, *, allow_review_spans: bool = False) -> dict[str, EvidenceSpan]:
    """THE GATE. Runs before any file is touched.

    For every GroundedValue in plan.fields:
      - if computed_from is set: every id in it must resolve via core.kb.get_span,
        and plan must carry a non-empty `calculation` string.
      - else: evidence_ref is REQUIRED and must resolve.
    For every Finding: every id in evidence_refs must resolve (min_length=1 already enforced).
    If a resolved span has needs_review=True and the value is numeric and
    allow_review_spans is False -> EvidenceResolutionError naming the field and span.

## The three renderers

### DOCX — `approval_note_v1.docx` via docxtpl (the R13 flagship)

Create the template with python-docx once, save it to `templates/`, then render with docxtpl.
Structure:

```
[ORG LETTERHEAD PLACEHOLDER]
INSPECTION APPROVAL NOTE                                    Ref: {{ task_id }}
Equipment: {{ fields.equipment_tag.value }}                 Date: {{ generated_on }}

1. SUMMARY
{{ title }}

2. FINDINGS
{% for f in findings %}
  {{ loop.index }}. [{{ f.severity|upper }}] {{ f.title }}
     {{ f.detail }}
     Source: {{ f.source_note }}          ← "Doc insp-2214, p.7" — built from resolved spans
{% endfor %}

3. MEASURED VALUES
  {% for k, v in fields.items() %}
  {{ k }} | {{ v.value }} {{ v.unit }} | {{ v.source_note }}
  {% endfor %}

4. CALCULATIONS                            ← R9: "calculations with steps shown"
  {% for c in calculations %}
  {{ c.label }}
    {{ c.expression }}
    {% for step in c.steps %}  {{ step }}{% endfor %}
    Result: {{ c.result }} {{ c.unit }}
    Independent re-derivation: {{ c.verified and "AGREES" or "DISAGREES — HUMAN REVIEW" }}
  {% endfor %}

5. RECOMMENDATION
{{ recommendation }}

Prepared by: {{ prepared_by }}
--------------------------------------------------
PROVENANCE  (auto-generated — do not edit)
{% for s in provenance %}[{{ s.span_id }}] {{ s.doc_id }} p.{{ s.page }} — "{{ s.text[:80] }}"
{% endfor %}
Receipt: {{ task_id }}.receipt.json
```

The provenance appendix is non-negotiable. It is what makes the document defensible after it
leaves the workbench, and it is the thing a CISO or an auditor will actually look at.

Amber-flag any value whose source span has `needs_review=True` with a visible marker:
`11.8 mm [⚠ low-confidence OCR — verify against original]`.

### PPTX — `board_deck_v1.pptx` via python-pptx

Deliberately simple. Five slide types, chosen by content, no layout engine:

1. Title slide — `plan.title`, date, `prepared_by`
2. Summary slide — bulleted `recommendation`
3. One slide per `Finding` — title, detail, severity colour bar, source footnote
4. Values table slide — `fields` as a 3-column table (name / value+unit / source)
5. Provenance slide — the span list, 8 pt

Use one built-in layout (`Title and Content`) for everything. Do not build a theming system,
do not add charts, do not compute layout. Fixed `Inches()` positions are correct here.

### XLSX — via openpyxl, no template file

Three sheets:
- `Summary` — title, recommendation, generated timestamp
- `Values` — one row per field: name, value, unit, evidence span_id, doc, page, needs_review
- `Calculations` — one row per step of each calculation, with the expression, substituted
  values, unit and the independent re-derivation result

Freeze the header row, bold headers, autosize columns, amber fill on `needs_review` rows.
Nothing else. No charts, no pivot tables, no conditional formatting engine.

## Calculations (R9)

`GroundedValue.calculation` holds the expression, and L4 will have run it through
`core.sandbox.verify_calculation()` before building the plan. Your job is only to **render the
steps that came back**, including the agreement verdict. Do not evaluate anything yourself —
`eval()` in the renderer would be both a security hole and a second source of truth.

If a plan contains a calculation whose verification disagreed, render it with a bold
`DISAGREES — HUMAN REVIEW REQUIRED` banner. Do not refuse to render; the human needs to see it.
